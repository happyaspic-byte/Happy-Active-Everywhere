# 중앙 웹 관리 사용법

중앙 서버 한 대의 웹 화면에서 여러 장치의 폴더와 동기화 작업을 관리합니다.
각 장치에는 everywhere 에이전트가 필요합니다. 파일 내용은 장치끼리 직접
교환하며, 중앙 서버에는 장치 정보·상태 보고·관리 명령이 저장됩니다.

이 기능은 구현 후 빌드·정적 검사 대상으로 추가되었습니다. 실제 장치 연결과
브라우저 사용 시험은 사용자가 수행합니다. 이전 동기화 엔진의 시험 결과를
새 중앙 관리 기능의 시험 결과로 간주하지 않습니다.

## 1. 중앙 서버 실행

[설치 안내](install-update.md)에 따라 서버 OS에 맞는 패키지를 설치합니다.
아래 `everywhere`는 설치한 실행 파일의 경로로 바꿔도 됩니다.
서버 상태는 에이전트 상태·동기화 폴더와 분리합니다.

```sh
everywhere central --state /absolute/path/central-state
```

처음 실행하면 새 상태 디렉터리와 서버 인증서를 만듭니다. 기존 디렉터리의
장치 신원은 교체하지 않습니다. 웹은 `127.0.0.1:7446`, 에이전트 제어 연결은
`0.0.0.0:7447`에서 대기합니다. 다른 터미널에서 로그인 토큰을 확인합니다.

```sh
everywhere management-token --state /absolute/path/central-state
```

서버의 브라우저에서 **http://127.0.0.1:7446**을 열고 토큰으로 로그인합니다.
토큰은 웹 탭 메모리에만 남으며 URL·시작 로그에는 넣지 않습니다.
장치가 접속할 서버의 LAN/VPN IP와 TCP 7447 연결 경로를 준비하세요.
다른 제어 포트는 첫 설정 때 `--control-listen 0.0.0.0:PORT`로 지정합니다.

## 2. 웹에서 장치 초대

1. **장치 → 장치 추가**를 누릅니다.
2. 초대 이름과 **장치에서 접속할 수 있는 중앙 서버 IP:7447**을 입력합니다.
   예: `192.168.1.10:7447`. 서버의 `0.0.0.0`을 입력하지 않습니다.
3. 내려받은 `everywhere-invitation.json`을 해당 장치에 전달합니다.

초대 파일에는 서버 공개 인증서와 일회용 등록 자격이 들어 있습니다. 등록할
장치에만 전달하세요. 24시간 안에 한 장치가 사용할 수 있습니다. 정상 등록의
응답만 유실된 경우 같은 장치·자격으로 다시 요청해도 등록을 중복 생성하지
않습니다. 사용된 초대 파일을 다른 장치에서 사용할 수는 없습니다.

## 3. 장치에 한 번 등록하고 에이전트 실행

해당 장치에 OS에 맞는 everywhere를 설치한 뒤 실행합니다.

```sh
everywhere enroll --state /absolute/path/device-state \
  --invitation /path/to/everywhere-invitation.json --name "작업용 Mac"
everywhere manage --state /absolute/path/device-state
```

Windows PowerShell 예:

```powershell
everywhere.exe enroll --state C:\EverywhereState --invitation "$env:USERPROFILE\Downloads\everywhere-invitation.json" --name "내 PC"
everywhere.exe manage --state C:\EverywhereState
```

등록 출력의 `device` 지문을 중앙 웹의 장치 지문과 대조하고 **장치 승인**을
누릅니다. 승인 전에는 원격 명령이 전달되지 않습니다. 서버 인증서는 초대
파일에 고정되므로 인증서가 다른 서버에 자격을 보내지 않습니다.
장치도 TLS 연결에서 개인키 소유를 증명하며, 중앙 서버는 등록·상태 요청이
그 장치의 인증서에서 온 것인지 확인합니다.

한 장치를 재시작할 때마다 등록할 필요는 없습니다. `manage`와 설치된 서비스가
`central-agent.json`을 읽고 재접속합니다. 이미 관리 서비스가 실행 중일 때
등록했다면 서비스를 재시작하세요. 기존 장치 상태에도 등록할 수 있으며 기존
파일·폴더·작업은 유지됩니다. 장치 상태를 다른 장치로 복제하지 마세요.

## 4. 폴더 연결

각 장치에 실제 동기화할 폴더를 준비한 뒤 웹의 **폴더 연결**에서 다음을 입력합니다.

- 폴더 ID: 두 장치에서 공유할 이름. 예: `personal`.
- 수신 대기 장치와 해당 장치의 전체 폴더 경로.
- 연결하는 장치와 해당 장치의 전체 폴더 경로.
- 장치별 양방향·보내기 전용·받기 전용 설정.
- 수신 대기 장치의 접속 가능한 IP:포트. 예: `192.168.1.20:7444`.

**폴더 연결 · 시작**은 각 장치에 인증서 신뢰, 폴더 접근 권한, 동기화 작업을
배포합니다. 수신 대기 포트는 해당 장치의 모든 인터페이스에서 열리지만 승인된
상대 인증서만 파일 프로토콜에 접근할 수 있습니다. 방화벽·라우터를 자동 변경하지
않으므로 LAN/VPN에서 두 장치 간 TCP 연결이 가능해야 합니다.

**명령 기록**에서 양쪽 배포 명령의 완료를 확인하세요. 한쪽이 오프라인이면 그쪽
명령은 대기합니다. 한쪽의 경로 오류로 실패해도 다른 쪽의 설정을 자동 삭제하지
않습니다. 오류를 고친 뒤 같은 설정으로 다시 배포할 수 있습니다. 이미 존재하는
폴더의 경로·모드나 기존 작업의 연결 대상이 다르면 거부합니다. 기존 일시정지는
재배포로 해제하지 않습니다.

세 번째 장치는 같은 폴더 ID로 기존 장치 한 대와 추가 연결합니다. 같은 수신
장치에서 새 상대와 연결할 때는 다른 수신 포트를 사용하세요. 현재 한 장치당
관리 작업은 최대 32개입니다. 중앙 등록 장치는 최대 128대입니다.

폴더를 최초 등록할 때 원래 엔진의 파일시스템 검사도 적용됩니다. 분리된 볼륨,
권한 오류, 지원하지 않는 파일시스템은 등록 실패로 표시됩니다. 오류를 빈 폴더나
정상 삭제로 취급하지 않습니다.

## 5. 일상 사용

**장치 상세**에서 폴더별 파일 수, 삭제 대기, 동시 변경과 작업 상태를 봅니다.
에이전트는 약 3초마다 접속하고 폴더 요약은 약 30초마다 갱신합니다. 20초 이상
접속 보고가 없으면 오프라인으로 표시합니다. 오프라인 화면은 마지막 보고 내용입니다.
폴더 요약이 제어 메시지 한도를 넘으면 일부 폴더만 표시하고 생략 사실을 알립니다.
명령 결과 전송·작업 제어는 유지됩니다.

- **일시정지 / 다시 시작**: 해당 장치의 해당 동기화 작업을 제어합니다.
  전체 연결을 정지하려면 관련 장치의 연결·수신 작업을 각각 정지합니다.
- **재검사**: 폴더 변경을 기록합니다. 실행 중 폴더 잠금과 경합하면 실패가
  표시될 수 있으므로 잠시 뒤 다시 요청하거나 관련 작업을 먼저 정지합니다.
- **삭제 승인 검토**: 실제 삭제된 경로와 검토 당시 버전을 보고 개별 승인합니다.
  검토 후 파일 상태가 바뀌면 기존 승인 요청을 거부합니다.
- **충돌 검토**: 보존된 각 버전 중 새 기준으로 사용할 내용을 선택합니다.
- **이전 버전**: 폴더 안의 상대 파일 경로를 입력해 보존 이력을 조회·복원합니다.
- **폴더 접근 회수**: 특정 상대의 해당 폴더 접근을 제거합니다. 명령이 적용된
  뒤 파일 프로토콜이 권한 회수를 확인합니다.

명령 등록은 실행 완료와 다릅니다. 웹의 **명령 기록**에서 결과를 확인하세요.
`실행 중`은 작업 프로세스가 있다는 뜻입니다. 실제 교환 완료는 각 작업의
**마지막 동기화 완료** 시각과 결과로 확인합니다. 전송 속도를 추정해 표시하지 않습니다.

## 6. 재시작·권한 회수·복구

중앙 명령 대기열과 장치의 실행 기록은 SQLite에 영속 저장합니다. 같은 명령 ID를
다시 받아도 완료된 파일 변경을 재실행하지 않습니다. 파일 반영 중 장치가 종료되어
결과를 기록하지 못했다면 **결과 확인 필요**로 보고합니다. 폴더 상태와 보존 이력을
확인한 뒤 필요한 작업만 새로 요청하세요. 실패가 이미 적용된 모든 작업의 자동
롤백을 뜻하지는 않습니다.

**중앙 관리 해제**는 새 중앙 명령을 차단하고 아직 전달하지 않은 명령을 취소합니다.
이미 실행 중인 명령이나 기존 P2P 동기화·폴더 접근 권한을 철회하는 기능은 아닙니다.
동기화도 차단하려면 먼저 관련 작업 정지·폴더 접근 회수를 요청하고 완료를 확인하세요.
오프라인 장치의 변경은 그 장치가 다시 연결되어 명령을 적용해야 효력이 생깁니다.

중앙 서버 백업은 서버를 정지하고 **중앙 상태 디렉터리 전체**를 보호된 위치에
보관하세요. `central.sqlite`뿐 아니라 서버 인증서·개인키·관리 토큰이 필요합니다.
기존 `device-backup`은 파일 동기화 장치의 백업 형식으로, 중앙 레지스트리 백업을
대체하지 않습니다. 파일 장치의 복구는 [장치 백업 안내](device-backup.md)를 따릅니다.
복구한 장치는 중앙에 다시 등록합니다. 과거 중앙 명령 저널·자격을 다른 신원으로
복사하지 않습니다.

## 7. 자동 실행

설치 패키지의 버전 관리 설치 경로를 사용합니다. 처음 중앙 설정을 준비할 때
`central`을 실행한 뒤 `Ctrl+C`로 종료하고 서비스를 등록할 수 있습니다.

```sh
# 중앙 서버 (중앙 설정 파일이 있는 별도 상태)
everywhere service install --state /absolute/path/central-state \
  --prefix /absolute/path/installed-everywhere --listen 127.0.0.1:7446

# 각 에이전트 (enroll을 마친 상태)
everywhere service install --state /absolute/path/device-state \
  --prefix /absolute/path/installed-everywhere --listen 127.0.0.1:7445
```

재시작·정지·상태 조회는 [서비스 안내](services.md)의 명령을 그대로 사용합니다.
서비스는 상태의 중앙 서버/에이전트 설정에 따라 역할을 선택합니다. 중앙 서버
정지는 장치에 이미 실행 중인 P2P 동기화를 정지하지 않습니다.

## 8. 다른 컴퓨터의 브라우저에서 접속

중앙 웹의 직접 외부 HTTP 노출은 허용하지 않습니다. SSH가 있는 서버라면:

```sh
ssh -N -L 7446:127.0.0.1:7446 USER@CENTRAL_SERVER
```

사용자 컴퓨터에서 `http://127.0.0.1:7446`에 접속합니다. 터널은 브라우저용이고,
장치 초대에는 여전히 각 장치에서 접속 가능한 중앙 제어 주소를 입력합니다.

상시 HTTPS 주소를 쓰려면 처음 서버를 구성할 때 `--public-origin`을 지정합니다.

```sh
everywhere central --state /absolute/path/central-state \
  --public-origin https://sync.example.com
```

신뢰하는 HTTPS 역방향 프록시가 동일 호스트의 `127.0.0.1:7446`으로 전달하도록
구성하고, 원래 `Host: sync.example.com`과 Origin을 유지하세요. HTTP 리다이렉트와
TLS 인증서는 프록시에서 처리합니다. 인증 헤더를 로그에 기록하지 않도록 구성합니다.
NAS Docker의 구체적인 포트·볼륨·프록시 설정은 NAS 모델과 운영 환경이 정해진 뒤
적용합니다. 현재 NAS 전용 이미지를 제공한다고 주장하지 않습니다.

현재 중앙 관리자는 하나의 관리 토큰을 사용하는 전체 권한 운영자입니다.
다중 사용자·SSO·역할별 권한·클러스터·NAT 릴레이·온디맨드 파일은 후속 범위입니다.
