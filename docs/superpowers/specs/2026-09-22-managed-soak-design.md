# Managed three-peer stability qualification

The full-product goal needs evidence from continuously running independent
agents, not only individually successful exchanges. Extend the existing CLI and
management acceptance flow with a repeatable, bounded, long-running controller.
It uses real `manage`, supervised `sync`/`sync-serve`, mutual TLS and local files.
No production fault-injection switches or new protocol are introduced.

## Runtime and authority

- Python 3.11+ standard library only; keep Rust dependencies unchanged.
- A run owns one newly created private local workspace and a copied immutable
  executable. Refuse an existing workspace. All data are synthetic; never use
  existing shares, unmount volumes, install OS services or remove user files.
- Three device identities, three persistent foreground managers and a ring of
  authenticated managed jobs exchange files through counting loopback TCP relays.
  Manager/worker process boundaries are real. This is not three physical devices.
- Managers receive parent-watch pipes so a controller crash closes the ownership
  chain and cannot silently leave unobserved synchronization running.
- Test-only keys/tokens and full state stay private locally. Never log bearer
  tokens or upload whole fixtures. Only reviewed summary JSON enters CI artifacts.
- Only the controller's own process handles may be killed. Retain failure
  evidence, versions, incoming/needed queues, history and journals for inspection.

## Cycle and independent oracle

Each cycle operates on a bounded set of paths and known generated bytes. Verify
the exact visible path/type set and independent SHA-256 payloads, including an
unchanged 256 KiB sentinel, Unicode names, an empty file and empty directory.
Compare normalized causal heads across devices and verify incoming/needed queues
drain; no unresolved or pending paths are silently discarded.

1. Create on A, await all peers, edit on B and await the reverse propagation.
2. Pause jobs, independently edit the same file on all three devices, scan, then
   reconnect in alternating ring orders. All three contents must remain in
   conflict objects and all heads and visible bytes converge. Explicitly choose
   one known revision and verify convergence to one head.
3. Pause jobs, delete on A and edit on B. Approve A's synthetic deletion, resume,
   and verify B's edit survives with the concurrent tombstone. Resolve explicitly.
4. Pause C, create a pending deletion on A, restart A's manager, verify pending
   state persists, approve the same reviewed deletion twice, sync A/B, reconnect
   stale C and verify the file does not return and tombstones agree everywhere.
5. Kill one managed worker or manager, confirm ownership cleanup and supervised
   or explicit restart, and verify subsequent bidirectional edits converge.
6. With no changes, rescan repeatedly and run continuous jobs for several
   iterations. Sequences/heads/file sets remain stable and counting relays must
   stay below a full sentinel transfer; empty queues alone are not the oracle.

Use authenticated management commands to pause/resume, approve reviewed deletions
and choose revisions. Pause jobs before exact CLI/DB snapshots to avoid treating
expected active-lock contention as a failed oracle. Only a documented busy lock
may be retried within a bounded deadline; other errors remain evidence.

The controller records an operation event before mutating a fixture and records
its result after verification. Store the expected manifest with each checkpoint.
A test controller interruption never counts as a completed stability run and is
not resumed as though observation continued. Start a separate run instead.

## Time, liveness and bounds

- A short smoke run and a 72-hour/7-day run use the same cycle. Success requires
  both the requested real elapsed duration and the minimum complete cycle count.
  Never substitute a large iteration count for elapsed time.
- Record monotonic and UTC observations. A gap exceeding 30 seconds interrupts
  continuous qualification; suspended hosts and stale reports cannot pass it.
- A run has a held OS lock, controller PID, run ID and atomic progress JSON.
  Read-only status checks current lock/process liveness and heartbeat age. A
  stale `running` file with no live owner is reported as interrupted.
- Check manager health and child ownership throughout waits. A requested fault
  may temporarily remove its named process; unexplained exits fail the run.
- Defaults: 120-second smoke, minimum two full cycles, 60 seconds between cycle
  starts, per-condition deadline 90 seconds, 4 GiB workspace limit and 2 GiB free
  space reserve. Limits stop with evidence, never trigger automatic pruning.
- Sample process RSS, relay bytes, workspace growth, cycle/phase latencies and
  failure counts. These measurements are same-host, uncontrolled-cache evidence.
- A 72-hour run may remain active across development turns. Publish its live
  handle and elapsed verified progress; do not declare its acceptance complete
  until its final independent state comparison and duration gate pass.
