# 지속 동기화 안정성 시험

`scripts/soak.py`는 새 임시 폴더 안에서 독립된 관리 프로세스 3개와 실제
동기화 작업 6개를 실행합니다. TCP 중계기를 거치는 상호 TLS 연결로 파일을
교환합니다. 같은 컴퓨터의 독립 프로세스 시험이며 물리 장치 3대, NAS,
실제 LAN/WAN 시험을 의미하지 않습니다.

Python 3.11 이상과 빌드된 CLI가 필요합니다. 외부 Python 패키지는 없습니다.
기존 폴더는 거부하며 합성 데이터만 생성합니다. 원본 사용자 폴더, 서비스
설치, 실제 볼륨 분리 또는 사용자 파일 정리는 수행하지 않습니다.

## 짧은 재현 시험

```sh
cargo build --locked
python3.11 -m unittest discover -s scripts -p test_soak.py -v
mkdir -p folder-report
python3.11 scripts/soak.py run \
  --binary target/debug/everywhere \
  --work-dir folder-report/managed-smoke-01 \
  --seconds 10 --min-cycles 2 --cycle-interval 0
```

Windows에서는 `python`과 `target/debug/everywhere.exe`를 사용합니다.
재실행할 때는 반드시 새로운 `--work-dir` 이름을 지정합니다. 실패한 폴더는
증거와 복구 점검을 위해 보존합니다. `--seconds 10`이어도 최소 두 주기가
끝나야 종료되므로 실행 시간은 10초보다 깁니다.

각 주기는 다음을 확인합니다.

| 시나리오 | 통과 조건 |
|---|---|
| A 생성 → B/C 수신 → B 수정 → A/C 수신 | 예상 경로·종류·내용 SHA-256 일치 |
| 세 장치 오프라인 동시 수정·다른 순서 재연결 | 세 수정본 보존, 버전 집합 일치, 명시적 해결 후 한 버전으로 수렴 |
| A 삭제·B 수정 | 수정본과 동시 tombstone 보존, 선택한 수정본으로 해결 |
| 삭제 승인 대기 중 A 재시작·중복 승인 | 동일 검토 내용 유지, 중복 승인은 409로 거부되며 상태 불변 |
| 삭제를 모르는 C 재접속 | 오래된 파일이 부활하지 않고 tombstone 일치 |
| B 관리 프로세스 강제 종료·재시작 | 기존 자식 종료, C의 후속 수정이 전체에 전파 |
| 원격 반영 후 반복 스캔·지속 연결 | 시퀀스·버전·큐 불변, TLS 바이트가 128 KiB 미만 |
| 최종 대조 | 현재 파일과 과거에 확인한 모든 보존 객체의 독립 SHA-256 일치 |

파일 집합에는 256 KiB 고정 파일, 빈 파일·디렉터리, 한글 경로가 포함됩니다.
모든 장치에서 내용이 똑같이 손상되어도 예상 내용과 비교하므로 실패합니다.
동기화 버전은 SQLite 읽기 전용 스냅샷으로 대조하고 삭제 대기·incoming·needed
큐가 남아 있으면 통과시키지 않습니다. TLS 바이트 제한은 변경 없는 구간의
전체 고정 파일 재전송을 잡는 검사이며 WAN 처리량 측정은 아닙니다.

## 실제 72시간 시험과 상태 조회

짧은 시험과 현재 커밋의 세 OS Actions가 통과한 뒤 실행합니다.

```sh
python3.11 scripts/soak.py run \
  --binary target/release/everywhere \
  --work-dir folder-report/managed-72h-01 \
  --seconds 259200 --min-cycles 2 --cycle-interval 60
```

다른 터미널에서 다음과 같이 확인합니다.

```sh
python3.11 scripts/soak.py status --work-dir folder-report/managed-72h-01
```

`status=running`과 `owner_live=true`는 현재 관측 중이라는 뜻입니다.
`qualification_72h=true`는 요청한 기간과 실제 관측 시간이 모두 72시간 이상이고,
최종 내용 검사와 프로세스 정리까지 통과했을 때만 기록합니다. 반복 횟수를
늘려 실제 경과 시간을 대신하지 않습니다. 7일은 `--seconds 604800`입니다.

UTC 또는 단조 시계의 관측 간격이 30초를 넘으면 연속 관측에 실패합니다.
컴퓨터 잠자기, 장시간 프로세스 정지, 컨트롤러 종료 후에는 새 시험으로
시작해야 합니다. 중단된 시험의 시간을 이어 붙이지 않습니다. 상태 파일만
남은 경우 현재 PID와 OS 잠금을 확인해 `interrupted`로 표시합니다.

관리 프로세스의 stdin 소유권을 감시하므로 컨트롤러 강제 종료 시 관리
프로세스와 그 동기화 작업도 종료됩니다. 정상 종료 경로에서는 모두 종료됐는지
확인합니다. 중계기 정리에 실패해도 다른 프로세스 정리를 계속하고 실패로
기록합니다. 테스트는 다른 프로그램의 PID를 종료하지 않습니다.

## 증거와 한계

- `summary.json`: 최종 상태, 실제 시간, 주기 수, 정리 결과와 측정값.
- `progress.json`: 현재 관측 상태. 직접 읽는 대신 `status`로 생존 여부도 확인합니다.
- `checkpoint.json`: 마지막 확인 시점의 예상 경로·SHA-256과 장치별 버전·큐.
- `events.jsonl`: 변경 전 기록, 검증 결과, 보존 객체 SHA-256과 주기 시간.
- `a/`, `b/`, `c/`: 장치별 파일·버전·DB·저널 및 프로세스 로그. 실패 시 읽을 수 있는 DB 스냅샷도 보존합니다.
- `everywhere` 및 `harness/`: 실행 파일과 시험 코드의 복사본. SHA-256을 기록하고 주기마다 재확인합니다.

메모리는 현재 관측한 관리·작업 PID의 RSS를 약 15초 간격으로 합산한 최댓값입니다.
Windows에서는 WorkingSet64를 사용합니다. 짧게 실행됐다 종료된 작업의 순간
최댓값을 포착한다는 보장은 없습니다. 관측값이 없으면 0 대신 null을 기록합니다.
저장 공간은 주기마다 점검하며 기본 한도는 작업 폴더 4 GiB, 여유 공간 2 GiB입니다.
한도에 도달하면 자료를 지우지 않고 실패로 중단합니다. 파일을 추가하는 중간
순간의 초과를 차단하는 디스크 할당량 기능은 아닙니다.

작업 폴더에는 합성 장치의 개인키가 있습니다. Unix에서는 새 작업 폴더를
0700으로 생성하며 Windows에서는 상위 폴더의 ACL을 따릅니다. 토큰은 로그에
남기지 않습니다. CI에는 `summary.json`만 올리고 전체 작업 폴더를 업로드하지
마세요. 시험 완료 후 자료 삭제는 운영자가 별도로 결정합니다.

이 시험 자체는 전원 손실, OS 재부팅, 실제 공간 부족·볼륨 분리, 100 GiB 또는
NAS 호환성을 검증하지 않습니다. [볼륨 장애 시험](volume-faults.md)과
[파일시스템 검증](storage-qualification.md)은 별도 결과입니다. 짧은 시험
통과나 72시간 시험 시작을 완제품 완료로 표시하지 않습니다.
